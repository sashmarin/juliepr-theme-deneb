# Agent instructions

## Project intent

This repository is a modern WordPress block theme for a blog. Prefer native WordPress Site Editor features, block markup, `theme.json`, and small, accessible components over legacy PHP-template patterns or framework-heavy abstractions.

The repository may begin with only scaffolding. When implementing a feature, first inspect the current tree and preserve established conventions. Do not invent a build system, dependency, or plugin requirement unless the task needs it and the choice is documented.

## Source of truth

- `theme.json` is the source of truth for design tokens, settings, styles, template parts, and editor-facing controls.
- Block templates belong in `templates/` and template parts in `parts/`.
- Reusable block patterns belong in `patterns/` and should be registered through standard WordPress conventions.
- PHP is appropriate for theme bootstrap, hooks, dynamic behavior, and narrowly scoped compatibility code. Keep presentation in block templates and patterns.
- JavaScript and CSS should be added only when core blocks, `theme.json`, or a small block style cannot provide the behavior.

## WordPress block-theme standards

- Follow the currently supported WordPress APIs and verify behavior against the project’s declared minimum WordPress version.
- Use valid block comment markup and keep template files editable in the Site Editor.
- Prefer semantic HTML and core blocks (`group`, `stack`, `row`, `query`, `post-template`, `post-featured-image`, `post-title`, `post-excerpt`, `navigation`, and similar) before custom blocks.
- Keep design decisions in `theme.json`: typography, spacing, layout widths, color palettes, gradients, border radii, and block-specific styles.
- Use presets and CSS custom properties generated by WordPress instead of hard-coded values where a design token exists.
- Keep templates and patterns composable. Avoid duplicating the same layout in multiple files when a template part or pattern is a better fit.
- Use translation functions for user-facing PHP strings and translation-ready metadata for patterns and theme text.
- Enqueue assets through WordPress APIs with predictable handles; do not load assets from CDNs without an explicit requirement.

## Accessibility and UX

- Treat accessibility as a feature requirement: keyboard navigation, visible focus, logical heading hierarchy, sufficient contrast, reduced-motion support, and meaningful link text.
- Do not use color alone to communicate state.
- Use responsive layouts and fluid typography/spacing; avoid fixed dimensions that cause overflow on small screens.
- Preserve the user’s ability to customize the theme in the Site Editor. Avoid CSS selectors or JavaScript that fight editor controls.
- Do not add autoplaying media, intrusive animations, or interaction patterns that require JavaScript when HTML/CSS can handle them.

## Security and compatibility

- Escape output at the point of rendering and sanitize stored or user-provided values.
- Use nonces and capability checks for privileged actions. Never trust request data.
- Avoid direct database access when a WordPress API exists.
- Do not modify WordPress core, generated files, or unrelated plugins.
- Keep backwards compatibility in mind for content authored with core blocks and for disabled optional features.

## Development workflow

Before editing:

1. Inspect the relevant files, `git diff`, and available scripts.
2. Identify the minimum WordPress/PHP/Node versions and existing lint/test commands.
3. Prefer a small, reversible change that matches the existing architecture.

After editing:

1. Validate JSON, PHP syntax, and block markup as applicable.
2. Run the project’s existing lint, test, build, or theme-check commands. If none exist, perform targeted validation and state what was checked.
3. Review the diff for accidental formatting changes, untranslated strings, accessibility regressions, and editor incompatibilities.
4. Report changed files, validation performed, and any remaining assumptions or manual Site Editor checks.

## Change boundaries

- Do not add unrelated theme features, branding, content, or dependencies.
- Do not rewrite existing files wholesale when a focused patch is sufficient.
- Do not remove user changes or use destructive Git commands.
- If a requested design cannot be implemented faithfully with core blocks and theme configuration, explain the trade-off before introducing custom infrastructure.

## Useful acceptance checks

For a theme change, check the relevant items below:

- The theme activates without PHP or JSON errors.
- Templates render valid, semantic block markup.
- The layout works at narrow, medium, and wide viewport sizes.
- Site Editor controls remain available and behave predictably.
- Posts, archives, search, 404, navigation, and featured images degrade gracefully when content is absent.
- Keyboard and screen-reader flows remain understandable.
- User-facing strings and pattern metadata are translation-ready.
